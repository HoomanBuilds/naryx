# Hyperliquid Testnet release values

Hyperliquid has no Naryx contract, so there is no deployment record here. `release.template.json` holds the reviewed operator configuration the API and solver load for `hypercore:testnet`: the domain manifest (its hash is computed with `packages/protocol-types`), market and token indexes, adapter, venue, and market manifest identities, order bounds, and the solver quote route.

Fill a copy outside the repository and pass it to `deployments/tools/release-manifests.mjs` with the shared release file. The generator writes `api/hyperliquid-testnet-runtime.json`, `solver/hyperliquid-testnet-quote.json`, the execution policy entry, and the env entries, loads them with `loadHyperliquidTestnetRuntimeConfig` and `loadHyperliquidTestnetQuoteRuntime`, and checks the asset indexes and size decimals against the public testnet `meta` and `spotMeta`. It never reads an agent key.

Execution is one reviewed switch: `definitions.executionEnabled`. With `false` the lane serves quotes only. With `true` the generated env turns on the API evidence runtime and executor client and the solver executor together, and writes every executor variable from `definitions.executor`: the approved agent wallet address and key file path (the path only), the master account and account kind, the spot universe, token names, token ids, and canonical flags, the perpetual name, minimum book depths, leverage mode, and the reference divergence bound. The generator then checks those names, token ids, canonical flags, and size decimals against the live testnet `meta` and `spotMeta`. The executor posts orders through the agent wallet to the trading account, and the keeper (`NARYX_KEEPER_PORT`, default 8789) serves its evidence, so the keeper must run beside it. Approve the agent wallet on the trading account and fund the account with Hyperliquid testnet USDC before setting `true`. Nothing here authorizes a mainnet action.

The trading account is an omnibus account. Users cannot fund Hyperliquid testnet accounts themselves, so this one funded account executes every user's package through the approved agent wallet: each package order names the user's own EVM wallet as owner and this trading account as settlement account, and the user's wallet signs the package authorization before execution. The executor runs one package at a time against the account (a durable lane in the solver journal database), reads the live account position under that lane, and targets this package's own delta, so reconciliation attributes the account-wide change to exactly one package. An outcome that is not final keeps the lane blocked until an operator releases it after recovery. The `omnibus` block of `api/hyperliquid-testnet-runtime.json` bounds fairness: open packages per owner wallet and the total entry notional the account carries; with no `omnibus` block the API refuses entries. The API keeps a per-owner ledger of open packages beside its execution store, so a user exits their own package from any device and never another user's.
